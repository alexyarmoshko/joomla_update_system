# Yak Shaver Joomla extensions update system (joomla_update_system)

Update servers for the Yak Shaver Joomla extensions: one update descriptor per extension, served as
raw XML to Joomla's Updater. Extensions are migrated here as they are released, so `manifests/` grows
over time and is the authoritative list of what this server answers for.

```
manifests/<extension>.update.xml     # plg_<group>_<element>, mod_<name>, com_<name>
```

## Use

An extension's manifest points at its own descriptor here:

```xml
<updateservers>
    <server type="extension" name="...">https://raw.githubusercontent.com/alexyarmoshko/joomla_update_system/refs/heads/main/manifests/<extension>.update.xml</server>
</updateservers>
```

Joomla polls that URL, compares `<version>` with the installed extension, downloads `<downloadurl>`,
and rejects the package unless it hashes to `<sha256>`.

| Property | Value |
|---|---|
| Served ref | `refs/heads/main` - branch head, never a tag |
| Tags | A record of what was served, and when |
| Visibility | Must stay public; `raw.githubusercontent.com` is fetched anonymously |
| Descriptor scope | Current release only - Joomla reads the file as it stands |
| Update site | Stored per site at install time, so a moved URL never reaches installed copies |

## Publishing

Each descriptor is **generated by the extension's own release build**, which fills in the download URL
and the checksum of the package it produced. Publishing is therefore:

1. Copy the generated descriptor over `manifests/<extension>.update.xml`.
2. Commit, tag.
3. Ensure the release asset it names is published, unchanged.

`<downloadurl>` and `<sha256>` are build output and are never edited here; every other field comes
from the extension's own template. The checksum describes one exact file, so re-building or replacing
a published asset invalidates it.
